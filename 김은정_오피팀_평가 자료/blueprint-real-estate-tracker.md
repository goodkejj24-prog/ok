# 부동산 시세 임장리스트 에이전트 시스템 설계서

> 작성일: 2026-03-17
> 목적: Claude Code 구현 참조용 계획서

---

## 1. 작업 컨텍스트

### 배경 및 목적
지정된 4개 지역(평촌, 용인, 금천, 서울 중랑구)의 25평 이하 아파트 실거래가를 매일 자동 수집하여, 전세가/전세 매물 수/3개월 전 대비 가격 변동을 한눈에 파악할 수 있는 웹 대시보드를 구축한다. 투자 후보 아파트를 빠르게 추려내고 임장 우선순위를 결정하는 데 활용한다.

### 범위
- **포함**: 아파트 시세 수집, 필터링, 시각화 대시보드, 일일 자동 업데이트, Firebase 저장
- **제외**: 사용자 인증/로그인, 매수/매도 주문, 중개사 연결, 모바일 네이티브 앱

### 입출력 정의

| 항목 | 내용 |
|------|------|
| **입력** | 네이버 부동산 크롤링 데이터 + 국토교통부 실거래가 공공 API |
| **출력** | Next.js 웹 대시보드 (Vercel 배포), Firebase Firestore에 일일 데이터 저장 |
| **트리거** | Vercel Cron Job — 매일 1회 (KST 06:00) 자동 실행 |

### 제약조건
- **기술적 제약**: 네이버 부동산 크롤링 시 rate-limit 준수 (요청 간 2초 딜레이), User-Agent 설정
- **운영 제약**: Vercel 무료 플랜 Cron 1일 1회, Firestore 무료 쿼터 (일 50K 읽기/20K 쓰기) 내 운영
- **품질 제약**: 크롤링 실패 시 이전 데이터 유지, 데이터 누락 시 대시보드에 "업데이트 실패" 표시

### 용어 정의

| 용어 | 정의 |
|------|------|
| 실거래가 | 국토교통부에 신고된 실제 매매 거래 가격 |
| 전세가 | 전세 계약의 보증금 가격 |
| 전세가율 | (전세가 / 매매가) × 100 — 갭투자 지표 |
| 임장 | 부동산 현장 답사 |
| 갭 | 매매가 - 전세가 (실투자금 추정) |
| 갭투자 | 전세 끼고 매수 — 실투자금 = 갭 + 취득세 + 중개수수료 |
| 토지거래허가구역 (토허제) | 지정 구역 내 매수 시 실거주 의무 부과, 전세 끼고 매수 불가 → 갭투자 불가 |
| 실투자금 | 갭투자 시: 갭 + 취득세(매매가×1.1%) + 중개수수료(매매가×0.4%) / 토허제: 매매가 전액 + 부대비용 |

## 2. 워크플로우 정의

### 전체 흐름도

```
[Cron Trigger 06:00 KST]
    → [Step 1: 아파트 마스터 목록 구축/갱신]
    → [Step 2: 실거래가 수집 (공공 API)]
    → [Step 3: 전세가 + 매물 수 수집 (네이버 부동산)]
    → [Step 4: 아파트 상세정보 수집 (네이버 부동산)]
    → [Step 5: 주변 인프라 정보 수집 (학교, 지하철)]
    → [Step 5.5: 선호도 + 입지환경 점수 수집/산출]
    → [Step 5.6: 토지거래허가구역 여부 확인]
    → [Step 6: 데이터 가공 + 3개월 전 비교 + 갭투자 분석 + 종합 랭킹]
    → [Step 7: Firebase Firestore 저장]
    → [Step 8: 프론트엔드 렌더링]
```

### LLM 판단 vs 코드 처리 구분

| LLM이 직접 수행 | 스크립트로 처리 |
|----------------|----------------|
| UI 디자인 의사결정 (pencil MCP) | 네이버 부동산 크롤링 (Puppeteer/Cheerio) |
| 코드 리뷰 및 품질 판단 | 공공 API 호출 및 파싱 |
| 테스트 시나리오 판단 (agent-browser) | 데이터 정제/변환/저장 |
| 아파트 필터링 기준 해석 | Cron 스케줄링, Firebase CRUD |

### 단계별 상세

#### Step 1: 아파트 마스터 목록 구축

- **처리 주체**: 스크립트 (`scripts/build-apartment-master.ts`)
- **입력**: 4개 지역 코드 (평촌/용인/금천/중랑구)
- **처리 내용**:
  - 네이버 부동산에서 지역별 아파트 목록 크롤링
  - 필터 적용: 25평 이하, 300세대 이상, 역 도보 15분 이내
  - 대형 아파트 밀집 지역 여부 확인
- **출력**: `apartments_master` 컬렉션 (Firebase Firestore)
- **성공 기준**: 각 지역에서 최소 1개 이상의 아파트가 추출됨
- **검증 방법**: 규칙 기반 (필터 조건 재검증)
- **실패 시 처리**: 자동 재시도 (최대 3회), 실패 시 이전 마스터 목록 유지 + 로그

#### Step 2: 실거래가 수집

- **처리 주체**: 스크립트 (`scripts/fetch-real-price.ts`)
- **입력**: 마스터 목록의 아파트 리스트 + 국토교통부 API 키
- **처리 내용**:
  - 국토교통부 아파트 매매 실거래가 API 호출
  - 최근 거래 + 3개월 전 거래 데이터 수집
  - 25평 이하 (전용면적 59㎡ 이하) 필터링
- **출력**: `real_prices` 컬렉션 (날짜별 실거래가 기록)
- **성공 기준**: API 응답 200, 파싱된 데이터 1건 이상
- **검증 방법**: 스키마 검증 (필수 필드: 단지명, 전용면적, 거래금액, 거래일)
- **실패 시 처리**: 자동 재시도 (최대 3회), 실패 시 스킵 + 로그

#### Step 3: 전세가 + 매물 수 수집

- **처리 주체**: 스크립트 (`scripts/fetch-jeonse.ts`)
- **입력**: 마스터 목록의 아파트 리스트
- **처리 내용**:
  - 네이버 부동산에서 아파트별 전세 실거래가 크롤링
  - 현재 전세 매물 수 카운팅
  - 요청 간 2초 딜레이 적용
- **출력**: `jeonse_prices` 컬렉션 (전세가 + 매물 수)
- **성공 기준**: 각 아파트에 대해 전세 데이터 수집 완료
- **검증 방법**: 규칙 기반 (전세가 > 0, 매물 수 >= 0)
- **실패 시 처리**: 개별 아파트 실패 시 스킵 + 로그, 전체 실패 시 재시도 (최대 3회)

#### Step 4: 아파트 상세정보 수집

- **처리 주체**: 스크립트 (`scripts/fetch-apartment-detail.ts`)
- **입력**: 마스터 목록의 아파트 리스트
- **처리 내용**:
  - 네이버 부동산에서 상세정보 크롤링
  - 수집 항목: 복도형/계단형, 난방방식(개별/중앙), 평균 관리비, 설립연도, 방 개수, 총 세대수
- **출력**: `apartment_details` 컬렉션
- **성공 기준**: 필수 필드 6개 모두 수집
- **검증 방법**: 스키마 검증 (hallwayType, heatingType, avgMaintFee, builtYear, roomCount, totalHouseholds)
- **실패 시 처리**: 누락 필드는 "정보 없음"으로 표시, 전체 실패 시 재시도 (최대 3회)

#### Step 5: 주변 인프라 정보 수집

- **처리 주체**: 스크립트 (`scripts/fetch-infrastructure.ts`)
- **입력**: 마스터 목록의 아파트 좌표/주소
- **처리 내용**:
  - 네이버 부동산 단지 상세에서 주변 학교 목록, 거리 정보 크롤링
  - 가장 가까운 지하철역 + 도보 소요시간 추출
대  - 강남역까지 대중교통 소요시간 (네이버 지도 or 카카오맵 API)
- **출력**: `infrastructure` 컬렉션 (학교 목록, 역 이름, 도보 시간)
- **성공 기준**: 최소 역 정보 1건 수집
- **검증 방법**: 규칙 기반 (역 도보 시간 <= 15분 필터 재확인)
- **실패 시 처리**: 스킵 + 로그, 이전 데이터 유지

#### Step 5.5: 선호도 + 입지환경 점수 수집/산출

- **처리 주체**: 스크립트 (`scripts/fetch-popularity.ts`)
- **입력**: 마스터 목록의 아파트 리스트
- **처리 내용**:
  - **네이버 부동산 선호도 수집**: 단지 페이지에서 관심(찜) 수, 최근 검색/조회 인기도 크롤링
  - **입지환경 종합 점수 산출** (100점 만점, 가중치 기반):

    | 항목 | 배점 | 산출 기준 |
    |------|------|----------|
    | 역세권 | 25점 | 도보 5분 이내 25점, 10분 이내 18점, 15분 이내 10점 |
    | 학교 접근성 | 20점 | 초등학교 500m 이내 +10, 중학교 1km 이내 +10 |
    | 단지 규모 | 15점 | 1000세대↑ 15점, 700세대↑ 12점, 500세대↑ 8점, 300세대↑ 5점 |
    | 주변 대단지 밀집 | 15점 | 1km 내 300세대↑ 단지 수 × 5점 (최대 15점) |
    | 연식 | 10점 | 5년 이내 10점, 10년 이내 8점, 15년 이내 5점, 20년↑ 3점 |
    | 전세가율 | 10점 | 80%↑ 10점, 70%↑ 7점, 60%↑ 4점 |
    | 관리비 | 5점 | 10만 이하 5점, 15만 이하 3점, 20만↑ 1점 |

  - 선호도 + 입지점수 기반 **종합 랭킹** 산출 (지역별 + 전체)
- **출력**: `popularity` 컬렉션 (찜 수, 입지점수, 종합랭킹)
- **성공 기준**: 각 아파트에 선호도 데이터 또는 입지점수 1개 이상 산출
- **검증 방법**: 규칙 기반 (입지점수 0~100 범위, 랭킹 중복 없음)
- **실패 시 처리**: 네이버 선호도 크롤링 실패 시 입지점수만으로 랭킹, 로그 기록

#### Step 5.6: 토지거래허가구역 여부 확인

- **처리 주체**: 스크립트 (`scripts/fetch-land-permit-zone.ts`)
- **입력**: 마스터 목록의 아파트 주소/법정동 코드
- **처리 내용**:
  - 국토교통부 토지거래허가구역 지정 현황 공공 API 또는 서울시 열린데이터 크롤링
  - 각 아파트의 법정동이 토허제 지정 구역에 포함되는지 매칭
  - 토허제 지정일, 해제 예정일(있을 경우) 수집
- **출력**: `land_permit_zone` 컬렉션 (아파트별 토허제 여부)
- **성공 기준**: 모든 마스터 아파트에 대해 토허제 여부 판정 완료
- **검증 방법**: 규칙 기반 (boolean 값 존재, 지정 구역 목록과 교차 검증)
- **실패 시 처리**: 판정 불가 시 "확인 필요"로 표시 + 로그

#### Step 6: 데이터 가공 + 3개월 전 비교 + 갭투자 분석 + 종합 랭킹

- **처리 주체**: 스크립트 (`scripts/process-data.ts`)
- **입력**: Step 2~5.6의 수집 데이터
- **처리 내용**:
  - 현재 매매가 vs 3개월 전 매매가 차이 계산 (금액, %)
  - 전세가율 계산 (전세가 / 매매가 × 100)
  - 갭(매매가 - 전세가) 계산
  - **갭투자 분석**:
    - 토허제 여부 판정 → 토허제 지역이면 `investType: "실거주(토허제지역)"` 표시
    - 비토허제 지역이면 `investType: "갭투자 가능"` 표시
    - **실투자금 산출**:
      - 갭투자 가능: 갭 + 취득세(매매가 × 1.1%) + 중개수수료(매매가 × 0.4%) = 실투자금
      - 토허제(실거주): 매매가 + 취득세 + 중개수수료 = 필요 자본금
  - 선호도(네이버 찜 수) + 입지환경 점수 병합
  - **종합 순위 산출**: 입지점수(60%) + 네이버 선호도 정규화(40%) → 종합점수 → **지역별 순위**
  - 데이터 병합 및 정렬 (지역별 → 종합 랭킹순 기본)
- **출력**: `daily_summary` 컬렉션 (가공 완료된 통합 데이터 + 랭킹 + 갭투자 분석)
- **성공 기준**: 모든 마스터 아파트에 대해 통합 레코드 + 순위 + 투자유형 생성
- **검증 방법**: 스키마 검증 (필수 필드 존재 + 수치 범위 체크 + 순위 연속성 + 투자유형 존재)
- **실패 시 처리**: 누락 아파트는 "데이터 수집 중"으로 표시

#### Step 7: Firebase Firestore 저장

- **처리 주체**: 스크립트 (`scripts/save-to-firebase.ts`)
- **입력**: Step 6의 가공 데이터
- **처리 내용**:
  - daily_summary를 날짜 키로 Firestore에 upsert
  - 90일 이전 데이터 자동 정리 (스토리지 절약)
  - 마지막 업데이트 타임스탬프 기록
- **출력**: Firestore 문서 갱신 완료
- **성공 기준**: Firestore 쓰기 성공, 타임스탬프 갱신됨
- **검증 방법**: Firestore 읽기로 저장 확인
- **실패 시 처리**: 자동 재시도 (최대 3회), 실패 시 로컬 JSON 백업 저장

#### Step 8: 프론트엔드 렌더링

- **처리 주체**: Next.js 앱 (자동 — 유저 접속 시)
- **입력**: Firestore의 daily_summary 데이터
- **처리 내용**:
  - 지역별 탭으로 아파트 리스트 표시
  - 각 아파트 카드에 상세정보, 시세, 인프라 정보 표시
  - 3개월 전 대비 가격 변동 시각화 (상승: 빨강, 하락: 파랑)
- **출력**: 웹 대시보드 화면
- **성공 기준**: 데이터 로딩 3초 이내, 모든 카드에 필수 정보 표시
- **검증 방법**: agent-browser 스킬로 시각적 테스트
- **실패 시 처리**: 에러 바운더리 표시 + Firestore 연결 재시도

### 상태 전이

| 상태 | 전이 조건 | 다음 상태 |
|------|----------|----------|
| IDLE | Cron 트리거 (매일 06:00 KST) | COLLECTING |
| COLLECTING | Step 1~5 완료 | PROCESSING |
| PROCESSING | Step 6 완료 | SAVING |
| SAVING | Step 7 완료 | COMPLETE |
| COMPLETE | 다음 Cron 트리거까지 대기 | IDLE |
| ERROR | 재시도 초과 | IDLE (이전 데이터 유지) |

## 3. 구현 스펙

### 폴더 구조

### CLAUDE.md 핵심 섹션 목록

- **프로젝트 개요**: 부동산 시세 추적 대시보드 — 역할과 목적
- **서브에이전트 호출 규칙**: designer → developer → tester 순서 및 트리거 조건
- **데이터 수집 규칙**: 크롤링 딜레이, API 호출 제한, 에러 핸들링 정책
- **코드 규칙**: Next.js App Router, TypeScript strict, shadcn 컴포넌트 사용 원칙
- **배포 규칙**: Vercel 배포 전 빌드 확인, 환경변수 체크

### 에이전트 구조

**구조 선택**: 멀티 에이전트 (오케스트레이터 + 서브에이전트 3개)

**선택 근거**: 사용자 요청에 따라 디자인/개발/테스트를 독립적 서브에이전트로 분리. 각 에이전트가 서로 다른 도구와 컨텍스트를 필요로 하며, 병렬 작업 시 컨텍스트 윈도우 최적화가 가능하다.

#### 메인 에이전트 (CLAUDE.md)
- **역할**: 전체 워크플로우 오케스트레이션, 서브에이전트 순차 호출 관리
- **담당 단계**: 서브에이전트 호출 순서 제어, 단계 간 데이터 핸드오프 확인

#### 서브에이전트 목록

| 이름 | 역할 | 트리거 조건 | 입력 | 출력 | 참조 스킬 |
|------|------|-----------|------|------|----------|
| designer | UI/UX 디자인 — pencil MCP로 화면 설계, 컴포넌트 구조 확정 | 프로젝트 초기 또는 UI 변경 요청 시 | 요구사항 문서 (이 설계서) | 디자인 스펙 (`design-spec.md`), 와이어프레임 | ui-designer |

## 6. Vercel Cron 설정

```json
// vercel.json
{
  "crons": [
    {
      "path": "/api/cron",
      "schedule": "0 21 * * *"
    }
  ]
}
```

> `0 21 * * *` = UTC 21:00 = KST 06:00 (매일)

### Cron API Route 실행 순서

```
/api/cron (route.ts)
  1. CRON_SECRET 헤더 검증
  2. build-apartment-master 실행 (최초 또는 주 1회)
  3. fetch-real-price 실행
  4. fetch-jeonse 실행
  5. fetch-apartment-detail 실행 (변경 시에만)
  6. fetch-infrastructure 실행 (변경 시에만)
  6.5. fetch-popularity 실행 (선호도 + 입지점수 산출)
  6.6. fetch-land-permit-zone 실행 (토허제 여부 확인)
  7. process-data 실행 (종합 랭킹 + 갭투자 분석 + 실투자금 산출)
  8. save-to-firebase 실행
  9. 실행 로그 저장
```

### daily_summary/{date} (문서 내 apartments 배열)

```typescript
{
  date: string;            // "2026-03-17"
  updatedAt: Timestamp;
  apartments: Array<{
    masterId: string;      // apartments_master 참조
    currentPrice: number;  // 현재 매매가 (만원)
    price3MonthsAgo: number; // 3개월 전 매매가 (만원)
    priceChange: number;   // 변동액 (만원)
    priceChangeRate: number; // 변동률 (%)
    jeonsePrice: number;   // 전세가 (만원)
    jeonseListingCount: number; // 전세 매물 수
    gap: number;           // 갭 = 매매가 - 전세가 (만원)
    jeonseRate: number;    // 전세가율 (%)
    // 선호도 + 입지환경
    naverInterestCount: number;  // 네이버 부동산 관심(찜) 수
    locationScore: number;       // 입지환경 종합 점수 (0~100)
    totalScore: number;          // 종합 점수 (입지 60% + 선호도 40%)
    rankRegion: number;          // 지역 내 순위
    // 갭투자 분석
    isLandPermitZone: boolean;   // 토지거래허가구역 여부
    investType: "갭투자 가능" | "실거주(토허제지역)"; // 투자 유형
    acquisitionTax: number;      // 취득세 (만원) — 매매가 × 1.1%
    brokerageFee: number;        // 중개수수료 (만원) — 매매가 × 0.4%
    realInvestment: number;      // 실투자금 (만원) — 갭투자: 갭+취득세+중개비 / 토허제: 매매가+취득세+중개비
  }>;
}
```
